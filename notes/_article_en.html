Never commit a secret in plaintext.

That is a rule your team has written down. Now here is a task:

Add a Postgres client to the ingestion service.

Compute the cosine similarity between those two strings. It is close to zero. They share no vocabulary, no topic, no surface structure. A top-k retrieval over a store containing that rule and a few thousand other entries will not return it.

So the rule is absent from context at exactly the moment the agent is about to write a connection string.

This is not a bad-embedding problem. A better model will not fix it, because the two texts genuinely are not similar — the retrieval is working correctly and returning the wrong thing. It is a category error in the architecture.

Why it’s a category error

Knowledge and rules have different trigger conditions.

A piece of knowledge is relevant when it resembles the question. “How does our auth flow work” should retrieve the auth ADR. Similarity is the right relevance signal, because the thing you need looks like the thing you asked.

A rule is relevant when it applies — when the current activity falls inside its scope. Its trigger condition is a predicate over the situation, not a resemblance to its own text. “Never commit a secret in plaintext” applies whenever code is being written. Nothing about that predicate is recoverable from the rule’s wording.

Retrieval by resemblance answers what looks like this?. Rules need an answer to what applies here?. Those are different queries, and running the second one through machinery built for the first gives you guardrails that fire when they happen to be topically adjacent to the risk, and stay silent otherwise.

Why this is a security problem, not a tuning problem

Anyone who has run detection at scale recognises the shape.

A rule that doesn’t fire produces no alert. No alert looks identical to no threat. The system reports success in both cases, and the only symptom of the broken one is an absence — nothing in the logs, nothing on the dashboard, nothing to page on. You find out when something lands in production, or when somebody audits by hand.

Vector-retrieved guardrails have precisely this property. The agent produces plausible output, the retrieval layer returns a normal-looking top-k, no error is raised anywhere, and the policy that should have blocked the action was simply never in the room. Every observable signal says the system worked.

Controls that fail open, without noise, are the worst class of control. Treating policy as one more thing to look up in a similarity index builds one of those by construction.

The fix is unglamorous: split the store

Two layers, retrieved differently, because they answer different queries.

LayerSizeRetrieval
Rules20–200 entriesScrolled in full by scope filter. Never searched.
Knowledge103–105 chunksSemantic search, top-k, filtered by project.

The rules layer is retrieved by payload filter on scope: everything active that applies globally, plus everything scoped to the current project. No ranking, no top-k, no embedding involved at retrieval time.

The objection is cost, and the objection doesn’t survive arithmetic. Keep the layer to 20–200 entries, cap each entry at 200 characters, and the whole thing is a few thousand tokens — noise next to a modern context window, and cheaper than a single wasted turn spent undoing an action a rule would have prevented.

The knowledge layer keeps everything else: ADRs, transcripts, code, postmortems, references. Similarity is the correct relevance signal there, and it scales.

The split is the whole idea. Everything below is what makes it hold up.

What a scrollable rule looks like

Scrolling the whole layer only works if the layer stays small, and it only stays small if the entries are disciplined. Four constraints, all of which are really the same constraint:

  1. Imperative. One rule per entry, stated as an instruction.
  2. Falsifiable. You must be able to say whether it was followed. If two people can disagree about compliance, it isn’t a rule.
  3. Under 200 characters. Reasoning goes in a separate rationale field, which is stored and never injected.
  4. No hedging. “Prefer”, “try to”, “where possible” produce entries that cannot be violated and therefore cannot be enforced. They cost context and buy nothing.

The second one can be checked. The first one is a mood.

Precedence, because rules conflict

Once you have a policy layer, you need a resolution order, and you need it written down rather than improvised per call.

  • Priority. Hard rule / strong default / preference. A hard rule is not worked around silently; if a session instruction contradicts one, the agent says so before complying.
  • Specificity. Project scope beats domain scope beats global scope.
  • Recency, only as a tie-break at equal specificity.
  • Unresolvable conflicts get surfaced, not arbitrated. Two active rules that genuinely contradict each other is a defect in the policy set. An agent that quietly picks one has hidden the defect instead of reporting it.

Supersede, never delete

A rule that stops being true is marked superseded and points at its replacement. It stays in the store, excluded from retrieval by its status.

This costs nothing and buys the history of what you tried and abandoned — which is the thing that stops a team from relitigating the same decision every eight months. Reserve outright retirement for rules that became meaningless: the project died, the tool is gone.

The predictable way this rots

Not data loss. Bloat.

The rules layer accumulates near-duplicates that disagree at the margins, and one day it no longer fits comfortably in context. The tempting fix at that point is to put a vector index in front of it.

Don’t. That reintroduces the original failure, and it does it at the exact moment the policy set is at its messiest — which is when you most need the whole thing visible.

An unscrollable rules layer is a signal to consolidate. Flag pairs above a similarity threshold as merge candidates. Flag rules never retrieved in N days as retirement candidates. Flag rules scoped to projects that no longer exist. Then have a human decide: the output of consolidation is a proposal, never an automatic edit. Silently rewriting your own policy set is a worse failure than the one you started with.

Scope of the claim

This isn’t specific to any vendor, framework, or vector database. It applies to any agent with both a knowledge store and a policy layer — which, increasingly, is any agent granted the ability to act.

The question to ask of your own setup is narrow and answerable: take your most important guardrail, take a task that would violate it, and check whether your retrieval layer actually returns the rule.

If it doesn’t, you don’t have a guardrail. You have a document.
